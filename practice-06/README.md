## 1. Цель работы

Цель работы — связать интерфейс браузерного приложения с учебным HTTP API и организовать предсказуемое состояние интерфейса во время асинхронных операций.

Отработаны навыки: отправка запросов GET, POST, PATCH и DELETE через `fetch`; передача JSON-тела и обработка ответов 200, 201 и 204; разделение общего HTTP-клиента, предметного API, контроллера и DOM-представления; вывод состояний `loading`, `ready`, `empty`, `error`; клиентская валидация формы; повторная загрузка данных после изменения на сервере; отмена запроса и защита от устаревшего ответа; безопасный вывод серверных данных через `textContent`.

Получено приложение, в котором категории и задачи поступают из учебного API, фильтры превращаются в query-параметры запроса, задача создаётся, редактируется, переводится в другой статус и удаляется, а сервер остаётся единственным источником данных.

## 3. Реализация

### 3.1. HTTP-клиент

Файл `src/api-client.js`. Функция `requestJson` принимает `method`, `body`, `query`, `signal` и `timeoutMs`.

- Допустимы только методы GET, POST, PATCH, DELETE; метод приводится к верхнему регистру. GET с `body` отклоняется до сетевого запроса.
- К каждому запросу добавляется `Accept: application/json`. При наличии тела выполняется `JSON.stringify` и добавляется `Content-Type: application/json`; запросам без тела этот заголовок не добавляется.
- Сначала проверяется `response.ok`: HTTP-ошибка сохраняет `status`, `code`, `details` и `url`. Затем статус 204 (возвращается `null`, `response.json()` не вызывается), затем `Content-Type` и корректность JSON.
- Тайм-аут (`AbortSignal.timeout`) и внешний `AbortSignal` объединяются через `AbortSignal.any`.
- Виды ошибок различимы: `http`, `network`, `invalid-response`, `timeout`, `aborted`.

### 3.2. Доменный API

Файл `src/task-api.js`. Реализованы операции: `getTasks`, `getTaskById`, `getCategories`, `loadInitialData` (задачи и категории загружаются параллельно через `Promise.all`), `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask`, `resetDemoData`.

Схема ответа проверяется в этом же модуле: `isTask` и `isCategory` проверяют поля записей, `validateCollection` — наличие массива `data`, уникальность `id` и совпадение `meta.total` с длиной коллекции. `deleteTask` ожидает строго `null`, иначе создаётся `ApiError` вида `invalid-response`. `resetDemoData` отправляет POST без тела. Модуль не работает с DOM и не формирует сообщения для пользователя.

### 3.3. Состояния интерфейса

| Состояние | Когда возникает | Представление |
|---|---|---|
| `loading` | запрос отправлен, ответа нет | сообщение о загрузке, `aria-busy="true"` |
| `ready` | получен непустой список | карточки и число найденных задач |
| `empty` | запрос успешен, результатов нет | явное сообщение без старых карточек |
| `error` | запрос завершился ошибкой | сообщение и кнопка «Повторить загрузку» |

Любая загрузка (`start`, `applyFilters`, `refresh`) сначала переводит интерфейс в `loading`. `empty` не считается ошибкой. Если начальная загрузка завершилась ошибкой и категории ещё не получены, кнопка повтора снова вызывает `loadInitialData`; когда категории уже есть, используется `getTasks`.

### 3.4. Изменение данных

Все изменения выполняются через одну функцию `performMutation` в `src/app-controller.js`:

```
блокировка кнопок → запрос изменения → успех → повторный GET с текущими фильтрами → разблокировка (finally)
                                      → ошибка → сообщение пользователю → разблокировка (finally)
```

- **Создание:** форма проверяется `validateTaskDraft`, затем `POST /tasks` с `title`, `priority`, `categoryId`; `id` и `completed` назначает сервер.
- **Редактирование:** `beginEdit` заполняет форму, `submit` отправляет `PATCH` с полями формы, поэтому значение `completed` сохраняется.
- **Смена статуса:** `PATCH` с `{ completed: !task.completed }`.
- **Удаление:** `DELETE`, ответ 204.
- После успешной операции список всегда запрашивается заново с сохранёнными фильтрами, поэтому интерфейс показывает только подтверждённое сервером состояние. `localStorage` не используется.

### 3.5. Защита от устаревшего ответа

1. Перед каждой новой загрузкой предыдущий запрос отменяется через `AbortController`.
2. Каждой загрузке присваивается порядковый номер `loadSequence`. Результат применяется, только если номер совпадает с последним, поэтому старый ответ не перезапишет новый, даже если запрос не удалось отменить.
3. Отмена (`kind: "aborted"`) считается штатным управлением потоком и пользователю как ошибка не показывается.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   Promise отклоняется только при сетевой проблеме или отмене. Ответ 404 — это полученный HTTP-ответ, поэтому статус нужно проверять явно через `response.ok`.

2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**
   У ответа 204 нет тела, а разбор пустой строки как JSON завершается ошибкой. Поэтому клиент возвращает `null` до попытки чтения JSON.

3. **Чем состояние `empty` отличается от `error`?**
   `empty` означает, что запрос выполнен успешно, но подходящих данных нет (результат фильтра или пустой набор); интерфейс показывает сообщение без старых карточек. `error` означает, что запрос завершился неудачей; интерфейс показывает сообщение об ошибке и кнопку повтора.

4. **Зачем отменять предыдущий запрос при смене фильтров?**
   При быстрой смене фильтров ответы могут прийти в другом порядке, и старый результат перезапишет новый. Отмена экономит ресурсы и предотвращает такую гонку. Дополнительная проверка номера запроса нужна на случай, если источник данных не отреагировал на сигнал отмены.

5. **Почему после мутации список повторно запрашивается у API?**
   Сервер — единственный источник данных. После изменения задача может перестать подходить под текущий фильтр или получить значения, назначенные сервером, поэтому интерфейс показывает только подтверждённое сервером состояние с учётом фильтров.

## 7. Вывод

Браузерный интерфейс (`dom-app.js`, `task-view.js`) не выполняет HTTP-запросов и работает только через контроллер. Контроллер (`app-controller.js`) управляет состояниями и сценариями, обращаясь к предметному API (`task-api.js`). Предметный API выбирает путь и метод и проверяет схему ответа, а общий HTTP-клиент (`api-client.js`) отвечает за заголовки, JSON, статусы, тайм-аут и отмену. Всё это опирается на контракт учебного API: пути, методы, коды 200, 201 и 204 и единый формат ошибок.

В ходе работы найдены и исправлены ошибки:

- лишний символ `\` в начале `app-controller.js`, из-за которого модуль не загружался;
- вызов `loadInitialData` после каждой мутации вместо повторного `GET` с текущими фильтрами;
- дублирование обработчиков кликов (на кнопках в `task-view.js` и делегирование в `dom-app.js`), из-за которого действия выполнялись дважды;
- класс `is-completed` был не на карточке задачи, а на элементе статуса;
- `resetDemoData` отправлял тело запроса, хотя по контракту его нет;
- лишний дубль функции `createTask` в конце `task-api.js`.

Итог: 70 проверок Node.js и 14 браузерных сценариев выполняются успешно.
