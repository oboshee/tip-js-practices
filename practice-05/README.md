Объяснение для отчёта (сопоставьте со своими метками):

- **Синхронный код** выполняется сразу и целиком, пока стек вызовов не опустеет; сюда относятся все `console.log` верхнего уровня и тела функций до первого `await`.
- **Микрозадачи.** Продолжения Promise (`.then`, `.catch`, код после `await`) и `queueMicrotask` попадают в очередь микрозадач. Она полностью выполняется сразу после текущего синхронного кода и до любой макрозадачи.
- **Таймер с задержкой 0.** `setTimeout(fn, 0)` не вызывает `fn` немедленно: функция ставится в очередь макрозадач и выполняется только после завершения синхронного кода и всех микрозадач.
- **Удаление обработчика Promise.** Если убрать `.then`, соответствующая метка исчезнет из вывода, а относительный порядок оставшихся меток не изменится: все микрозадачи по-прежнему идут раньше таймера.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP API (инфраструктура): маршруты `/health`, `/tasks`, `/tasks/:id`, `/categories`, отладочные маршруты `/debug/*`, CORS и формат ошибок. |
| `src/api-client.js` | Общий HTTP-клиент: сборка URL, заголовки, тайм-аут и отмена, проверка статуса и `Content-Type`, разбор JSON, класс `ApiError`. Ничего не знает о задачах. |
| `src/task-api.js` | Предметный слой: `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`; нормализация фильтров и проверка формы данных по контракту. |
| `src/variant.js` | Номер варианта и соответствующий ему набор фильтров. |
| `src/main.js` | Точка входа консольного клиента: создаёт клиент, выполняет запрос по фильтрам варианта и выводит результат. |

**Почему `fetchFn` передаётся в `createApiClient`.** Клиент не зависит от глобального `fetch`: в проверках подставляется поддельная функция, поэтому поведение клиента (ошибки, статусы, неверный JSON) проверяется без сети и воспроизводимо.

**Почему HTTP-ошибки проверяются отдельно от сетевых.** `fetch` отклоняет Promise только при сетевой проблеме или отмене; ответы 404 и 503 — это полученные ответы, поэтому статус проверяется явно через `response.ok`. Тип ошибки определяет реакцию вызывающего кода (повторить запрос, показать сообщение сервера, сообщить об отсутствии соединения).

**Почему JSON проверяется по контракту.** Синтаксически корректный JSON не гарантирует нужную структуру: сервер может вернуть не те поля или несогласованный `meta.total`. Предметный слой проверяет данные до использования и при несоответствии выбрасывает `ApiError` вида `invalid-response`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `parseBaseUrl` проверяет абсолютный http/https-адрес без query и hash; `buildUrl` убирает лишние `/` на стыке базы и пути | `buildUrl("http://127.0.0.1:5505/api/", "/tasks", …)` даёт `…/api/tasks?…` |
| Кодирование query | Параметры задаются через `URL.searchParams.set`; пустые значения (`undefined`, `null`, `""`) пропускаются | `q: "модель & тест"` → `q=%D0%BC…+%26+%D1%82%D0%B5%D1%81%D1%82` |
| Заголовок `Accept` | `Accept: application/json` добавляется к каждому запросу | Модульная проверка клиента |
| Проверка `response.ok` | Выполняется первой; при ошибке создаётся `ApiError` вида `http` с `status`, `code`, `details`, `url` из тела ошибки | Задача 999 → `http`, 404 |
| Проверка `Content-Type` | После успешного статуса требуется `application/json`, иначе `invalid-response` | `/debug/text` → `invalid-response` |
| Разбор JSON | `response.json()` в `try/catch`; ошибка разбора → `invalid-response` | `/debug/invalid-json` → `invalid-response` |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`; по умолчанию 2000 мс | Задержка 300 мс при лимите 20 мс → `timeout` |
| Внешняя отмена | Внешний `AbortSignal` объединяется с тайм-аутом через `AbortSignal.any` | `abort()` → `aborted` |

## Последовательная и параллельная загрузка

Сравнение двух способов получения задач и категорий через `/debug/delay` (одинаковые задержки):

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---|---|---|---|
| Два последовательных `await` | _измерить_ | _измерить_ | _измерить_ | _общее время ≈ сумме задержек_ |
| `Promise.all` | _измерить_ | _измерить_ | _измерить_ | _общее время ≈ наибольшей задержке_ |

Пояснение для вывода: при последовательных `await` второй запрос начинается только после ответа на первый, поэтому времена складываются. В `Promise.all` оба запроса уходят сразу и ожидаются одновременно, поэтому общее время определяется самым долгим из них. Точные значения зависят от компьютера и сети, поэтому в отчёте сравниваются только свои измерения.

## Вывод

Реализован общий HTTP-клиент и предметный модуль чтения задач для учебного API. Клиент разделяет виды отказов, и вызывающий код реагирует на них по-разному:

- **Ожидание Promise** — запрос ещё выполняется; результат или отказ придёт позже, интерфейс не блокируется.
- **HTTP-ошибка** (`http`) — сервер ответил, но с неуспешным статусом (404, 400, 503); у ошибки есть `status`, `code` и `details`.
- **Сетевая ошибка** (`network`) — ответа нет (сервер недоступен, соединение разорвано), статуса и кода нет.
- **Неверный ответ сервера** (`invalid-response`) — статус успешный, но тело не JSON, JSON повреждён или не соответствует контракту.
- **Тайм-аут** (`timeout`) — ответ не получен за установленное время; запрос прерывается клиентом.
- **Явная отмена** (`aborted`) — запрос прерван вызывающим кодом через `AbortController`; это не сбой сервера.
